# P126 — Unified Communications and Production Inbox

P126 is the communications layer on top of V125's production provider runtime. It turns the V122 conversation/message tables into a durable operator inbox with provider-backed outbound delivery, inbound webhooks, delivery receipts, unread state and human handoff.

## What is now real

- Tenant-scoped conversation queue with channel, assignment, unread count and last inbound/outbound timestamps.
- Message timeline API with opaque content references instead of message bodies in PostgreSQL.
- Atomic outbound message + durable `communication.message.send` job creation.
- V125 provider runtime is the only outbound provider execution path.
- Postmark email, Twilio SMS/voice and WhatsApp Cloud outbound channels.
- Postmark inbound/delivery webhook normalization.
- Twilio inbound/status callback normalization with signed-request verification.
- WhatsApp Cloud webhook verification challenge and signed POST verification.
- Replay-safe webhook identity and message idempotency.
- Durable sent/delivered/read/failed receipt reconciliation.
- Optimistic read and human handoff operations.
- Lease-bound worker RPCs so a worker can read/update only a message belonging to its leased job.
- Deployment-reviewed encrypted content-store boundary for message bodies and attachments.

## API surface

Authenticated:
- GET /api/v1/platform/inbox/conversations
- GET /api/v1/platform/inbox/conversations/:id/messages
- POST /api/v1/platform/inbox/conversations/:id/messages
- POST /api/v1/platform/inbox/conversations/:id/read
- POST /api/v1/platform/inbox/conversations/:id/handoff
- GET /api/v1/platform/inbox/webhooks
- POST /api/v1/platform/inbox/webhooks

Public provider ingress:
- POST /api/v1/inbox/webhooks/:one-time-endpoint-token
- GET /api/v1/inbox/webhooks/:one-time-endpoint-token for WhatsApp verification

The endpoint token is stored only as a SHA-256 hash and is returned once when the endpoint is provisioned.

## Outbound contract

A send request must include:
- exact conversation id
- exact provider connection id
- matching channel
- content reference generated by the reviewed content store
- recipient
- client idempotency key
- explicit consent=true
- explicit approved=true

Atlas creates the message and queue job in one database transaction. The worker uses a maximum of one attempt for provider delivery. V125's reconciliation policy remains in force because providers do not universally guarantee exactly-once external side effects.

## Content boundary

Message bodies, HTML, attachments and raw provider payloads are not placed into PostgreSQL rows or queue payloads. The API and worker load a deployment-reviewed content module.

The production module must use encrypted object storage/KMS, tenant-scoped authorization, retention policy and attachment scanning. The repository ships only a fail-closed example.

## Webhook security

Postmark does not provide HMAC webhook signatures. P126 therefore uses the provider's documented HTTP Basic Auth pattern and keeps event deduplication in the database. Postmark recommends HTTPS, Basic Auth and IP allowlisting for webhook protection.

Twilio webhooks are verified with X-Twilio-Signature using the account authentication token or configured webhook shared key. The validation input includes the exact webhook URL and request parameters.

WhatsApp Cloud POSTs are verified with X-Hub-Signature-256 and the configured Meta app secret. The GET challenge uses the one-time endpoint token as the configured verify token.

## Deployment requirements

Set:
- ATLAS_INBOX_CONTENT_MODULE
- ATLAS_WEBHOOK_SECRET_RESOLVER_MODULE
- ATLAS_INBOX_CONTENT_PATH
- ATLAS_WEBHOOK_SECRETS_PATH

The webhook secret resolver returns provider-specific secrets without persisting them in PostgreSQL. The content module returns only bounded content to the worker and must not log customer data.

Apply migrations through V126 and the V126 API grants before enabling the inbox. Then provision one endpoint per tenant/provider connection and configure the provider webhook URLs.

## Production truth boundary

P126 is code-complete for the repository contract, but a deployment is not automatically Live. A real deployment still needs:
- managed PostgreSQL with V126 applied
- real KMS/object storage content module
- real webhook secret resolver
- verified provider connections
- provider webhook configuration
- HTTPS/WAF/rate limiting
- sandbox delivery tests followed by controlled live delivery
- provider receipt and reconciliation monitoring
- backups/restore and load/failure evidence

No source file or adapter presence is treated as proof that a provider account is connected.
