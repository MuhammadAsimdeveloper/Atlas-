## Per-feature completion contract

Every benchmark capability in packages/atlas-feature-catalog/index.mjs must progress through:

1. Mapped — unique immutable feature ID, domain, stage and Atlas anchor.
2. Contract — domain behavior and security invariants exist and have automated tests.
3. Build complete — UI/API/storage/runtime implementation is present where required and integration tests exercise it.
4. Deployment verified — real provider/infrastructure behavior is tested in the intended production boundary.
5. Released — release gate, rollback path and operational evidence are present.

A feature is not complete because a placeholder, UI card, catalog entry or marketing claim exists.

## Non-negotiable hardening

Each feature must respect tenant scope. Risky features use idempotency, replay protection, least privilege and explicit approval. Financial operations use integer minor units and balanced journals. Communications re-check consent/suppression at dispatch. AI tools cannot receive raw credentials or escape their authorized tenant/tool boundary. Production releases require observability and rollback evidence.

## Integration strategy

Atlas will not hand-build thousands of bespoke integrations as isolated code paths. The connector SDK provides the common provider contract, auth model, operation/scopes model, webhook verification, sync checkpoint, rate limiting, health, idempotency and conflict-resolution primitives. Provider implementations then become declarative adapters on top of that stable interface.

## External boundary

Live credentials, carrier registration, DNS/CDN/WAF, managed PostgreSQL/Redis/object storage/KMS, production SSO, payment processing, model providers, compliance assessment and verified scale are deployment evidence, not source-only claims.
